UML(Unified Modeling Language)은 객체지향 분석·설계 결과를 그림으로 표준화해 표현하는 표기법이다. 특정 프로그래밍 언어나 방법론에 묶이지 않고, 시스템의 구조와 동작을 이해관계자가 공통으로 읽을 수 있게 만드는 것이 목적이다. 정처기 필기에서는 UML 자체보다 "이 다이어그램이 구조적(정적)이냐 행위적(동적)이냐"를 구분하는 문제로 자주 나온다.

## 구조적 다이어그램과 행위적 다이어그램

UML 다이어그램은 크게 두 갈래로 나뉜다.

구조적(정적) 다이어그램은 시스템을 구성하는 요소와 그 관계를 보여준다. 시간의 흐름과 무관하게 무엇이 있고 어떻게 연결되어 있는지를 그린다. 클래스 다이어그램, 객체 다이어그램, 컴포넌트 다이어그램, 배치 다이어그램, 패키지 다이어그램이 여기 속한다.

행위적(동적) 다이어그램은 시스템이 실행되는 동안 요소들이 어떻게 상호작용하고 상태가 어떻게 바뀌는지를 보여준다. 유스케이스 다이어그램, 시퀀스 다이어그램, 협력(커뮤니케이션) 다이어그램, 상태 다이어그램, 액티비티 다이어그램이 여기 속한다.

시험에서 자주 걸리는 함정은 유스케이스 다이어그램이다. 이름 때문에 구조적으로 오해하기 쉽지만, 실제로는 액터와 시스템 기능의 관계를 다루는 행위적 다이어그램으로 분류된다. 순서나 흐름을 그리지 않는데도 행위적에 속한다는 점은 원리보다는 UML 표준 분류로 그대로 외워두는 편이 낫다.

## 클래스 다이어그램의 관계

클래스 다이어그램은 구조적 다이어그램 중 가장 많이 다뤄진다. 클래스 사이의 관계는 강도에 따라 나뉜다.

```text
연관(Association):       Class A ------- Class B   (단순히 안다)
집합(Aggregation):       Class A <>----- Class B   (전체-부분, 부분은 독립적으로 존재 가능)
합성(Composition):       Class A <#>---- Class B   (전체-부분, 부분은 전체에 종속)
일반화(Generalization):   Class A ----|> Class B   (상속, B가 A의 하위 타입)
```

집합과 합성을 가르는 기준은 부분이 전체 없이도 존재할 수 있는가다. 자동차와 바퀴는 자동차가 폐차돼도 바퀴는 남을 수 있으니 집합, 사람과 심장은 사람이 사라지면 같이 의미를 잃으니 합성으로 보는 식이다. 이 구분이 정처기 필기에 반복해서 나온다.

## 유스케이스와 시퀀스 다이어그램

유스케이스 다이어그램은 액터(사람 또는 외부 시스템)와 유스케이스(시스템이 제공하는 기능) 사이의 관계를 그린다. 여기서 include는 한 유스케이스가 실행될 때 다른 유스케이스를 반드시 포함해서 실행하는 관계이고, extend는 특정 조건에서만 선택적으로 실행되는 확장 관계다. 로그인을 거치지 않고는 주문하기가 성립하지 않으면 include, 포인트 적립처럼 특정 상황에서만 덧붙는 동작이면 extend로 구분한다.

시퀀스 다이어그램은 객체 사이에 주고받는 메시지를 시간 순서로 그린다. 각 객체는 세로선인 생명선(lifeline)으로 표현되고, 객체가 메시지를 처리하는 활성 구간은 활성 박스(activation bar)로 표시한다. 메시지 화살표의 방향과 순서만 봐도 어떤 객체가 어떤 객체를 호출하는지 파악할 수 있어, 설계 단계에서 상호작용 흐름을 검증하는 데 쓰인다.

## 시험에 자주 나오는 포인트

구조적 vs 행위적 분류에서는 유스케이스 다이어그램의 소속을 헷갈리지 않아야 한다. 클래스 다이어그램의 집합과 합성은 개념뿐 아니라 표기 기호(속이 빈 마름모 vs 채워진 마름모)까지 함께 외워두면 실수를 줄일 수 있다. 유스케이스의 include와 extend는 필수냐 선택이냐라는 기준 하나만 기억해두면 헷갈릴 일이 적다.
