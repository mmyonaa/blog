## 요구사항 공학이란

요구사항 공학(Requirements Engineering)은 사용자가 원하는 시스템이 무엇인지 파악해 문서로 만들고, 그것이 올바른지 검증하며, 개발 중 변경을 관리하는 활동 전체를 말한다. 개발 후반에 요구사항 오류를 발견할수록 수정 비용이 크게 늘어나기 때문에, 초기 단계에서 정확히 잡는 것이 목적이다.

## 요구사항의 분류

| 구분 | 설명 | 예 |
|---|---|---|
| 기능 요구사항 | 시스템이 수행해야 할 기능 | 회원 가입, 주문 취소 |
| 비기능 요구사항 | 품질·제약 조건 | 응답 시간 2초 이내, 24시간 가용 |

시험에서는 성능, 보안, 신뢰성, 사용성 같은 항목이 비기능 요구사항으로 분류된다는 점을 묻는다. 이 밖에 사용자 요구사항(사용자 관점의 서술)과 시스템 요구사항(개발자 관점의 상세 서술)으로 나누기도 한다.

## 4단계 프로세스

### 1. 요구사항 도출 (Elicitation)

이해관계자로부터 요구를 수집하는 단계다. 인터뷰, 설문, 관찰, 워크숍(JAD), 프로토타이핑, 유스케이스, 브레인스토밍 등이 쓰인다. 이해관계자마다 말하는 내용이 다르고 암묵적 요구가 빠지기 쉬워서 여러 기법을 섞는다.

### 2. 요구사항 분석 (Analysis)

수집한 요구사항 사이의 충돌, 모호함, 누락을 찾아 정리하는 단계다. 우선순위를 정하고 실현 가능성을 따지며, 구조적 분석이나 객체지향 분석으로 모델링한다. 자료 흐름도(DFD), 유스케이스 다이어그램, 클래스 다이어그램이 대표적인 도구다.

### 3. 요구사항 명세 (Specification)

분석 결과를 정해진 형식의 문서로 기록한다. 대표 산출물이 소프트웨어 요구사항 명세서(SRS, Software Requirements Specification)다. 명세는 개발자와 사용자가 모두 같은 의미로 읽을 수 있어야 하며, 자연어로 쓰면 모호해지기 쉬워 모델이나 정형 기법을 병행하기도 한다.

### 4. 요구사항 확인 (Validation)

명세가 사용자의 의도를 제대로 반영했는지 검증하는 단계다. 방법으로는 검토(리뷰), 워크스루, 인스펙션, 프로토타입 검증, 테스트 케이스 작성 등이 있다. 이 단계에서 완전성, 일관성, 검증 가능성 같은 속성을 점검한다.

## 좋은 요구사항의 조건

```text
- 명확성: 한 가지 의미로만 해석된다
- 완전성: 필요한 내용이 빠지지 않았다
- 일관성: 요구사항끼리 충돌하지 않는다
- 검증 가능성: 만족 여부를 측정·시험할 수 있다
- 추적성: 출처와 설계·구현·테스트까지 연결된다
```

예를 들어 "시스템은 빨라야 한다"는 측정할 수 없어 검증이 불가능하다. "검색 결과는 대부분의 경우 2초 이내에 표시된다"처럼 기준을 정량화해야 한다. 이때 '대부분'도 모호하므로 실제로는 "95% 요청"처럼 비율까지 정한다.

## 요구사항 관리

개발 중에도 요구사항은 바뀐다. 변경 요청을 공식 절차로 접수해 영향도를 분석하고 승인하며, 버전을 관리한다. 요구사항 추적표(Traceability Matrix)로 요구사항과 설계·코드·테스트 케이스의 연결을 유지하면 변경 시 영향 범위를 빠르게 파악할 수 있다.

## 시험 포인트

- 4단계 순서는 도출 - 분석 - 명세 - 확인이며, 각 단계의 활동을 짝지어 묻는다.
- 도출 기법(인터뷰, JAD, 프로토타이핑)과 분석 도구(DFD, 유스케이스)를 구분한다.
- 산출물 SRS는 명세 단계의 결과물이다.
- 비기능 요구사항은 성능·보안·신뢰성 같은 품질 속성이다.
- 추적성은 요구사항 관리의 핵심 속성이다.
