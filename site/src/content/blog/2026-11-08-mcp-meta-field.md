MCP 서버를 만들다 보면 "이 요청에 추적 ID를 하나 붙이고 싶다", "결과에 처리 시간을 같이 돌려주고 싶다" 같은 요구가 생긴다. 스펙에 없는 필드를 아무 데나 끼워 넣으면 다른 구현과 충돌하거나 검증에서 걸릴 수 있다. MCP는 이런 용도로 `_meta`라는 자리를 열어 두었다.

## _meta란

`_meta`는 요청 파라미터, 결과, 알림 등 여러 메시지에 붙을 수 있는 선택 필드로, 키-값 객체다. 본래 의미(도구 인자, 도구 출력)와 분리된 부가 정보를 담는 통로다. 도구의 `arguments`에 추적 ID를 섞으면 도구 스키마가 오염되지만, `_meta`에 두면 도구 입력과 구분된다.

스펙이 직접 쓰는 대표 사례가 진행 상황 알림이다. 클라이언트가 요청의 `_meta.progressToken`에 토큰을 실어 보내면, 서버는 그 토큰으로 진행률 알림을 돌려보낼 수 있다.

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "summarize",
    "arguments": { "url": "https://example.com" },
    "_meta": {
      "progressToken": "job-42",
      "com.example/trace-id": "a1b2c3"
    }
  }
}
```

여기서 `progressToken`은 스펙이 정의한 키이고, `com.example/trace-id`는 우리가 임의로 붙인 키다.

## 키 이름 짓는 규칙

충돌을 막으려면 키 이름에 규칙이 필요하다. 스펙의 관례는 대략 다음과 같다(정확한 문구는 사용하는 스펙 버전에서 확인하자).

- 키는 선택적 접두사와 이름으로 구성하고, 접두사가 있으면 `/`로 구분한다.
- 접두사는 점으로 이어진 라벨 형태이며, 보통 소유한 도메인을 역순으로 쓴다(`com.example/`).
- `modelcontextprotocol`이나 `mcp`로 시작하는 라벨이 들어간 접두사는 MCP 자체용으로 예약되어 있으니 쓰지 않는다.

자기 조직의 접두사를 붙이면 남의 구현이나 훗날 스펙에 추가될 키와 이름이 겹칠 가능성이 크게 줄어든다.

## 서버에서 다루는 태도

서버 쪽에서는 몇 가지를 지키는 편이 안전하다.

```text
1. 모르는 _meta 키는 에러로 처리하지 않고 무시한다.
2. 비즈니스 로직의 필수 입력을 _meta에 넣지 않는다.
3. 민감 정보(토큰, 개인정보)를 _meta에 싣지 않는다. 로그에 그대로 남기 쉽다.
4. 응답의 _meta는 요청의 _meta를 그대로 돌려주는 용도가 아니다. 필요한 값만 따로 담는다.
```

핵심은 `_meta`가 "없어도 동작해야 하는 정보"를 위한 자리라는 점이다. 클라이언트가 `trace-id`를 안 보내도 도구는 정상 동작해야 하고, 보냈다면 로그에 남기는 정도로 쓴다.

## 정리

- `_meta`는 스펙 밖 부가 정보를 도구 입력·출력과 분리해 싣는 선택 필드다.
- `progressToken`처럼 스펙이 쓰는 키가 이미 존재한다.
- 자체 키는 `com.example/name`처럼 도메인 접두사를 붙이고, MCP 예약 접두사는 피한다.
- 모르는 키는 무시하고, 필수 로직과 민감 정보는 `_meta`에 두지 않는다.

서버를 직접 만드는 입장에서는 추적·계측 같은 횡단 관심사를 `_meta`로 빼 두면 도구 스키마를 깨끗하게 유지할 수 있다.
